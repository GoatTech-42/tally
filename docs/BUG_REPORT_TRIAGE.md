## Report spam and follow-up rules

Updated manual reporters send the capability-gated anonymous installation key. The live receiver advertises at most two new reports per installation in ten minutes and a consolidation warning for subsequent submissions. Older clients omit this key and cannot reliably be treated as the same reporter. Worker deduplication is a separate service and still requires independent verification.

Repeats of the same problem should retain material new evidence under one canonical job. Different problems from one installation remain valid. Distinct confirmed reporters can raise priority within severity bounds; same-installation repeats must not inflate it. Never infer a person from a shared IP, a receiver bot's GitHub author, or generic IOException.

Confirmed financial loss or unsafe exposure changes take priority over popularity. Keep missing data unknown. A released related patch is not confirmation that a particular report is resolved. Do not request unfiltered logs, raw settings, player/home names or credentials to fill these gaps.

## Follow-up — October 17, 22:28 UTC

Controller-level repeat-cycle fixtures reproduce another order-desk stall independently of missing logs: a server-confirmed cancelled row still reserved its market, active slot and unfilled funds, preventing a replacement. Cancelled rows with deliveries also queued repeated collection even after those goods were accounted for, and used the delivered quantity instead of the original requested quantity in the collection key. The patch releases only cancelled unfilled reservations, preserves uncollected-goods holds, and deduplicates/bounds collection attempts with the original key.

Related symptoms: #56, #85, #89, #92. This is a reproduced code defect and a patch for that path, not proof that every report had a cancelled order or the same cause. Their filtered excerpts do not contain that evidence. The existing quote-refresh fix and improved reviewed diagnostics remain included; report-specific confirmation is still required.
## Additional pass — October 17, 22:35 UTC

A two-Flip controller fixture also reproduces duplicate replenishment planning: PLACE for the first item succeeds, then QUOTE for the second item replans against a native own-order book that predates that placement. The fix adopts only the driver's immutable native page containing a matching active placed order. Receipt-only success, or a page with only old completed/cancelled matches, invalidates the old read and requires native refresh before quote replanning. This is a separate reproduced defect; it does not establish the cause of the historical single-item reports.
## Collection retry pass — October 17, 22:41 UTC

Three controller regressions reproduce another repeat-cycle defect: collection attempt counts were used as row ordinals, old collected rows consumed that same failure budget, and a successful collection never reset it. A retry could skip the only real row, or several otherwise successful lots could eventually stop collecting permanently. New collection passes begin at ordinal zero, historical-row traversal is separate from a failed complete pass, and confirmed collections clear failures for their exact key. Six successive lots with increasing historical rows remain collectable. The four-failed-pass hold and actual outstanding goods remain protected. This is a reproduced code path related to #56/#85/#89/#92, not report-specific confirmation from their old excerpts.
## Order identity pass — October 17, 22:47 UTC

Regressions reproduce three more order-selection/accounting defects. The collector matched item/price while controller keys and row ordinals also depended on requested quantity, so an older differently sized order could steal the target. Cancellation also matched closed historical rows before the active row. Finally, a late fill interrupting CANCEL queued COLLECT with CANCEL's zero quantity, giving it the wrong accounting key. Collections now carry their known requested quantity into native matching, cancellation considers active rows only, and late-fill cancellation rereads the native book before collection. Refused requests cannot mutate a current row target. Related symptoms remain unconfirmed for #56/#85/#89/#92; these tests establish code defects, not those reports' exact historical cause.
## Disabled Send report button — October 17, 23:45 UTC

The in-game reporting screen's capability gate accepted at most 4 KiB, while the expanded public receiver capability response was measured at 6,298 bytes with diagnostic support available. The gate therefore rejected a valid response and left Send report disabled. Manual and automatic reporting now use one bounded 8 KiB reader. A regression using expanded metadata failed before the limit correction; boundary, oversized, invalid-JSON and unsuccessful-response cases remain covered. This confirms an in-game code defect, but the original user's reporting surface has not been identified. Web-panel busy, cooldown, successful-submission and status-unavailable states are separate.

## Flip ceiling refresh — October 18, 00:26 UTC

Report #102 contains a pre-stop TOP_BID_CEILING gate; the stopped capture does not establish why earlier ordering failed. A controller regression independently reproduces a stale ceiling rejection: a 90-second-old native bid of 950 plus the configured increment 100 exceeds a maximum 1000, but the planner queued no refresh because the quote still met its ordinary 15-minute lifetime. Later own-order reads kept repeating the same rejection. The planner now rate-limits a fresh native quote on later desk passes; when the new native bid is 100 it can plan at 200 under the original ceiling. Fresh ceiling rejections neither place orders nor spam quotes. This fixes a reproduced path related to #102 without claiming report-specific confirmation or overriding price/stock/safety limits.
